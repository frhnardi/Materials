01

Opening — Kenapa Kita Belajar Terraform

~20 mnt▶

Selamat datang. Anggap aja ini hari pertama kamu masuk "tim infra". Di akhir modul ini kamu bakal bisa bikin infrastruktur AWS cuma dari kode — VPC, subnet, security group, EC2 yang jalanin Nginx — terus hapus semuanya lagi dengan satu perintah. Rapi, bisa diulang, dan ke-track di Git.

Apa yang bakal kamu bangun

Sepanjang modul, kamu naik level pelan-pelan lewat lab kecil sampai akhirnya bikin capstone project: sebuah web app sederhana di AWS (VPC + subnet publik + security group + EC2 + Nginx + S3 + remote state) yang semuanya dideklarasikan pakai Terraform. Cost-aware, jadi dompet aman.

Terraform itu apa, sih?

Terraform adalah tool Infrastructure as Code (IaC) buatan HashiCorp. Intinya: kamu nulis file teks yang mendeskripsikan "infrastruktur yang aku mau kayak gini", lalu Terraform yang ngurusin gimana caranya bikin itu beneran ada di AWS lewat API.

Bayangin kamu mau bangun rumah. Cara lama: kamu telepon tukang satu-satu, instruksiin manual ("pasang pintu di sini, jendela di situ"). Tiap mau bangun rumah baru, ngulang dari nol dan gampang lupa.

Terraform itu kayak blueprint/denah rumah. Kamu tulis sekali, kasih ke "kontraktor" (Terraform), dan dia yang eksekusi sesuai gambar. Mau bangun 10 rumah identik? Tinggal pakai blueprint yang sama. Mau bongkar? Kasih perintah bongkar, beres.

Kenapa ini penting banget buat Cloud/DevOps Engineer

  • Repeatability — infra dev, staging, prod bisa dibikin identik. Gak ada lagi "kok di prod beda ya, padahal di staging jalan".
  • Auditability — semua perubahan infra lewat Git. Siapa ngubah apa, kapan, kenapa — kelihatan di history & pull request.
  • Collaboration — tim review perubahan infra kayak review kode biasa, sebelum di-apply.
  • Disaster recovery — region kebakaran? Tinggal terraform apply di region lain. Infra-nya udah jadi kode.
  • Speed + konsistensi — klik manual 40 resource di Console itu lama dan rawan typo. Kode gak pernah capek dan gak salah klik.

Bukan berarti Console jelek

Console tetap berguna buat eksplorasi, debugging, dan lihat-lihat. Tapi untuk infra yang kamu pakai serius & berulang, IaC jauh lebih aman. Pola umum: eksplor di Console, produksi di Terraform.

"Declarative" itu maksudnya gimana?

Terraform itu declarative: kamu mendeskripsikan kondisi akhir yang diinginkan ("aku mau 1 EC2 t3.micro di subnet publik"), bukan langkah-langkahnya ("nyalain instance, tunggu, attach ENI, ..."). Itu lawannya imperative.

Declarative = pesan di restoran: "Aku mau nasi goreng pedas." Kamu gak ngajarin chef cara masaknya.
Imperative = kamu masuk dapur dan ngasih instruksi tiap langkah: "panaskan wajan, tuang minyak, ...".
Terraform = kamu kasih "menu" akhir, dia yang mikirin urutan masaknya. Kalau kamu jalanin lagi dan kondisinya udah sesuai, dia gak masak ulang (ini disebut idempotency).

  • asdf — multi-tool (Terraform, Node, Python, dll).

Project Pertama — S3 Bucket

~40 mnt▶
🧪 Lab 1

Kita mulai dari yang aman & murah: bikin satu S3 bucket. Bucket gratis dibikin (bayar kalau diisi data besar / banyak request), jadi sempurna buat lab pertama.

Struktur project

terraform-s3-basic/ ├── main.tf # resource utama (bucket) ├── variables.tf # input yang bisa diubah ├── outputs.tf # nilai yang ditampilkan setelah apply └── versions.tf # kunci versi Terraform & provider

versions.tf

versions.tf
terraform {
  required_version = ">= 1.10"          # minimal versi Terraform

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"                 # izinkan 6.x, tahan dari breaking 7.x
    }
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
  }
}

Penjelasan: required_version mengunci versi Terraform CLI. required_providers mendaftar plugin yang dibutuhkan beserta batas versinya. ~> 6.0 artinya "boleh 6.x apa pun, tapi jangan loncat ke 7.0" (proteksi dari breaking change major).

main.tf

main.tf
# provider AWS — "penerjemah" ke API AWS
provider "aws" {
  region = var.aws_region
}

# nama bucket S3 harus unik SE-DUNIA, jadi kita tambah suffix acak
resource "random_id" "suffix" {
  byte_length = 4
}

# resource utama: satu S3 bucket
resource "aws_s3_bucket" "lab" {
  bucket = "${var.bucket_prefix}-${random_id.suffix.hex}"

  tags = {
    Project   = "belajar-terraform"
    ManagedBy = "terraform"
    Env       = "lab"
  }
}

# best practice: matikan akses publik secara eksplisit
resource "aws_s3_bucket_public_access_block" "lab" {
  bucket                  = aws_s3_bucket.lab.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

Baris per baris: random_id bikin 4 byte acak → di-render jadi hex (8 karakter). Kita gabung ke nama bucket biar gak tabrakan sama orang lain (ingat, namespace bucket itu global!). aws_s3_bucket.lab.id di resource kedua = implicit dependency: Terraform otomatis tau bucket harus jadi dulu sebelum public access block.

variable "env" {

  common_tags = {
    Project   = "myapp"

Variable vs Local — bedanya?

Variable = input dari luar (bisa diubah saat apply). Local = nilai turunan internal, gak bisa di-override dari luar. Pakai local buat menghindari pengulangan (DRY), mis. common_tags yang dipasang ke semua resource.

Sensitive variables

sensitive.tf
variable "db_password" {
  type      = string
  sensitive = true   # nilainya disembunyikan dari output CLI
}

output "db_password_out" {
  value     = var.db_password
  sensitive = true   # WAJIB kalau output menyentuh nilai sensitif

Catatan penting soal sensitive = true

Ini cuma menyembunyikan nilai dari tampilan CLI. Nilainya tetap tersimpan plain di state file. Kita bahas tuntas di chapter Keamanan ("kenapa sensitive ≠ aman 100%").

Functions, conditional, for, dynamic

expressions.tf
# FUNCTIONS — built-in, banyak banget
locals {
  upper_env  = upper(var.env)              # "DEV"
  joined     = join("-", ["a", "b"])       # "a-b"
  bucket     = lower("MyApp-${var.env}")   # "myapp-dev"
  az_count   = length(["a", "b", "c"])     # 3
}

# CONDITIONAL (ternary): kondisi ? jika_benar : jika_salah
locals {
  instance_type = var.env == "prod" ? "t3.medium" : "t3.micro"
}

# FOR expression — transform list/map
locals {
  upper_names = [for n in ["web", "db"] : upper(n)]   # ["WEB", "DB"]
}

# DYNAMIC block — bikin block berulang dari data
resource "aws_security_group" "web" {
  name = "web-sg"
  dynamic "ingress" {
    for_each = var.allowed_ports          # mis. [80, 443]
    content {
      from_port   = ingress.value
      to_port     = ingress.value
      protocol    = "tcp"
      cidr_blocks = ["10.0.0.0/16"]
    }
  }
}
Kapan pakai dynamic?

Saat jumlah block (mis. rule ingress) bergantung pada variable/data, bukan jumlah tetap. Jangan over-pakai — kalau cuma 2 rule fix, tulis manual lebih kebaca.

AWS Provider — Lebih Dalam

~30 mnt▶

Provider adalah jembatan ke API AWS. Tanpa provider, Terraform cuma tahu sintaks tapi gak ngerti "EC2" atau "S3" itu apa.

Mendaftarkan provider

versions.tf
terraform {
  required_version = ">= 1.10"
  required_providers {
    aws = {
      source  = "hashicorp/aws"   # alamat di Terraform Registry
      version = "~> 6.0"          # constraint versi provider
    }
  }
}
  • source — alamat provider di registry (hashicorp/aws).
  • version — batas versi provider (per modul ini, AWS provider terbaru di seri 6.x).
  • required_version — versi Terraform CLI-nya.
CLI version vs Provider version

Dua hal beda! Terraform CLI = mesin inti (mis. 1.14.6). AWS provider = plugin yang dirilis terpisah (mis. 6.47.0) dan punya siklus rilis sendiri. Keduanya di-pin terpisah.

Konfigurasi provider & autentikasi

provider.tf — cara aman
provider "aws" {
  region  = var.aws_region
  profile = var.aws_profile   # pakai named profile dari AWS CLI
}

Terraform mencari kredensial AWS secara berurutan (mirip AWS SDK):

  1. Environment variables: AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN
  2. Shared config/credentials file (~/.aws/credentials) via profile
  3. AWS SSO / IAM Identity Center
  4. IAM Role yang di-attach ke instance/CI (mis. lewat OIDC)

Assume Role

assume-role.tf
provider "aws" {
  region = var.aws_region
  assume_role {
    role_arn     = "arn:aws:iam::123456789012:role/terraform-deployer"
    session_name = "terraform-session"
  }
}

Konsep assume role: identity-mu "meminjam" role lain yang punya izin spesifik, dapet kredensial sementara (auto-expire). Ini pola standar buat cross-account & CI/CD yang aman.

JANGAN hardcode access key

Apa itu terraform.tfstate?

State locking & drift

Locking = saat satu orang lagi apply, orang lain dikunci biar gak nabrak (state corrupt). Drift = saat realita AWS berbeda dari state (mis. ada yang ngubah security group lewat Console). terraform plan akan mendeteksi drift dan nawarin "betulin balik".

Inspeksi state dengan aman

terraform refresh masih ada?

Masih ada tapi di-deprecate sebagai perintah berdiri sendiri. Cara modern: terraform apply -refresh-only atau terraform plan -refresh-only — lebih aman karena kamu lihat dulu apa yang berubah sebelum state di-update.

Import resource yang sudah ada

Punya resource yang dibikin manual dan mau "diadopsi" ke Terraform? Pakai import. Cara modern (deklaratif) pakai import block:

  to = aws_s3_bucket.legacy
  id = "nama-bucket-yang-udah-ada"
}

}

Lalu terraform plan akan nunjukin rencana import. (Cara lama: terraform import aws_s3_bucket.legacy nama-bucket — masih jalan, tapi import block lebih bisa di-review lewat PR.)

taint sudah usang — pakai -replace

Dulu buat maksa bikin ulang resource pakai terraform taint. Sekarang di-deprecate. Cara modern:

Jangan pernah buka terraform.tfstate di editor lalu ubah manual — kecuali kamu benar-benar paham konsekuensinya dan sudah backup. Salah edit = Terraform "amnesia" → bisa bikin dobel atau hapus resource salah. Pakai perintah terraform state resmi (mv, rm) kalau perlu manipulasi, itu pun hati-hati.

Remote Backend dengan S3

~45 mnt▶
🧪 Lab 2

Saatnya pindahin state dari laptop ke S3 biar aman & bisa dishare tim.

UPDATE PENTING: locking sekarang pakai S3 native (bukan DynamoDB)

Dulu state locking di S3 backend butuh tabel DynamoDB terpisah. Sejak Terraform 1.10 ada fitur use_lockfile (S3 native locking), dan sejak 1.11 fitur ini sudah GA (stable). Akibatnya argumen dynamodb_table kini deprecated dan akan dihapus di versi minor mendatang. Karena kita pakai Terraform 1.14.x, kita pakai use_lockfile = true dan tidak perlu DynamoDB lagi. Lebih murah, lebih sedikit IAM, lebih simpel.

Langkah 1 — Siapkan bucket backend (sekali saja)

Bucket buat nyimpen state idealnya dibikin terpisah (chicken-and-egg: backend butuh bucket, tapi bucket dibikin Terraform). Banyak tim bikin bucket ini via CLI manual / project bootstrap terpisah. Contoh via AWS CLI:

bootstrap.sh
REGION=ap-southeast-1
BUCKET=tfstate-belajar-$(openssl rand -hex 4)

# buat bucket (di luar us-east-1 wajib LocationConstraint)
aws s3api create-bucket \
  --bucket "$BUCKET" --region "$REGION" \
  --create-bucket-configuration LocationConstraint="$REGION"

# versioning: WAJIB, biar bisa rollback state
aws s3api put-bucket-versioning \
  --bucket "$BUCKET" \
  --versioning-configuration Status=Enabled

# enkripsi default (SSE)
aws s3api put-bucket-encryption --bucket "$BUCKET" \
  --server-side-encryption-configuration \
  '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}'

# blokir akses publik
aws s3api put-public-access-block --bucket "$BUCKET" \
  --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

echo "Backend bucket: $BUCKET"

Langkah 2 — Konfigurasi backend block

backend.tf — cara modern (1.10+)
terraform {
  backend "s3" {
    bucket       = "tfstate-belajar-xxxxxxxx"
    key          = "terraform/aws-basic/terraform.tfstate"
    region       = "ap-southeast-1"
    encrypt      = true
    use_lockfile = true   # <- S3 NATIVE LOCKING (pengganti DynamoDB)
  }
}

Saat di-apply, Terraform bikin file kunci kecil ...terraform.tfstate.tflock di S3 selama operasi berlangsung, lalu hapus setelah selesai. Itu yang mencegah dua orang apply barengan.

Kalau masih lihat tutorial DynamoDB?

Tutorial dengan dynamodb_table itu pra-1.10 dan masih bekerja (dengan warning deprecated). Untuk migrasi mulus, kamu boleh set dynamodb_table DAN use_lockfile = true bersamaan sementara, lalu lepas DynamoDB. Untuk project baru di 1.14.x, langsung use_lockfile = true saja.

Kenapa backend block gak bisa pakai variable biasa?

Backend dikonfigurasi sangat awal saat init, sebelum Terraform mengevaluasi variable/locals. Jadi nilai di blok backend harus literal. Solusinya: pakai backend config file atau flag -backend-config.

backend-dev.hcl
bucket = "tfstate-belajar-xxxxxxxx"
key    = "terraform/dev/terraform.tfstate"
region = "ap-southeast-1"
terminal
terraform init -backend-config=backend-dev.hcl

Langkah 3 — Migrasi local state ke remote

Kalau sebelumnya kamu udah punya state lokal, tambahkan backend block lalu:

terminal
terraform init -migrate-state   # Terraform tawarin copy state lokal ke S3
# ketik 'yes' saat ditanya

Kalau cuma ubah konfigurasi backend yang sama (mis. nambah use_lockfile), pakai terraform init -reconfigure.

Jangan berbagi satu state untuk banyak environment

Pisahkan state per environment lewat key berbeda, mis. terraform/dev/terraform.tfstate vs terraform/prod/terraform.tfstate. Kalau dev & prod nempel di satu state, salah apply dev bisa ngerusak prod. Lebih bagus lagi: bucket/akun terpisah untuk prod.

IAM minimal buat backend (dengan locking)

{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": ["s3:ListBucket"],
      "Resource": "arn:aws:s3:::tfstate-belajar-xxxxxxxx" },
    { "Effect": "Allow",
      "Action": ["s3:GetObject","s3:PutObject","s3:DeleteObject"],

Terraform membangun dependency graph otomatis lalu mengeksekusi resource dengan urutan benar (yang independen bisa paralel).

Karena aws_subnet.a menyebut aws_vpc.main.id, Terraform tahu VPC dibuat dulu. Kamu gak perlu nulis apa-apa tambahan.

Kadang ada ketergantungan yang tidak terlihat lewat atribut (mis. IAM policy harus aktif sebelum suatu aksi). Di situ pakai depends_on.

explicit.tf
resource "aws_instance" "app" {
  # ...
  depends_on = [aws_iam_role_policy.app_policy]  # pastikan policy ready dulu
}
Jangan obral depends_on

Lifecycle Rules

~25 mnt▶

Blok lifecycle mengatur cara Terraform memperlakukan resource saat update/replace.

create_before_destroy

cbd.tf
resource "aws_instance" "web" {
  # ...
  lifecycle {
    create_before_destroy = true   # bikin pengganti dulu, baru hapus lama
  }
}

Default Terraform: hapus dulu, baru bikin (bisa downtime). Dengan ini: bikin yang baru dulu → tukar → baru hapus lama. Bagus buat zero-downtime replace.

prevent_destroy — rem darurat

prevent.tf
resource "aws_s3_bucket" "important_data" {
  bucket = "data-penting-perusahaan"
  lifecycle {
    prevent_destroy = true   # Terraform NOLAK kalau ada rencana hapus ini
  }
}

Cocok buat bucket data penting / database produksi. Kalau ada destroy yang menyentuh resource ini, Terraform gagal dengan error — penjaga dari kecelakaan.

ignore_changes

ignore.tf
resource "aws_instance" "web" {
  # ...
  lifecycle {
    ignore_changes = [
      ami,                    # jangan replace cuma karena AMI baru
      tags["LastScanned"],    # tag yang diubah tool lain di luar TF
    ]
  }
}

replace_triggered_by

replace-trigger.tf
resource "aws_instance" "web" {
  # ...
  lifecycle {
    replace_triggered_by = [aws_launch_template.web.latest_version]
  }
}

Memaksa replace resource ini saat resource/atribut lain berubah — berguna saat ketergantungan tidak otomatis memicu replace.

Jangan salah pakai

ignore_changes yang berlebihan bikin kode & realita "diam-diam" beda (kamu sengaja buta terhadap drift). prevent_destroy bisa bikin destroy seluruh stack gagal di tengah jalan. Pakai dengan sadar, dokumentasikan alasannya.

~50 mnt▶
🧪 Lab 4

Module itu kayak fungsi di pemrograman: bungkus sekumpulan resource jadi satu unit reusable dengan input (variables) & output.

Bayangin resep "EC2 web server". Daripada nulis ulang VPC+SG+EC2 tiap project, kamu jadiin module. Project lain tinggal "panggil" module itu sambil isi parameter (region, instance type). Sekali bikin bagus, dipakai di mana-mana.

Root module vs Child module

  • Root module = folder tempat kamu jalanin terraform apply.
  • Child module = module yang "dipanggil" dari root (lokal atau remote).

Struktur Lab 4

terraform-modules-demo/ ├── main.tf # root: panggil module ├── variables.tf ├── outputs.tf └── modules/ └── ec2-web/ # child module reusable ├── main.tf ├── variables.tf └── outputs.tf

variable "instance_type" { type = string  default = "t3.micro" }
variable "tags"          { type = map(string)  default = {} }

modules/ec2-web/main.tf

modules/ec2-web/main.tf
data "aws_ami" "al2023" {
  most_recent = true
  owners      = ["amazon"]
  filter { name = "name"  values = ["al2023-ami-*-x86_64"] }
}

  ami                    = data.aws_ami.al2023.id
  instance_type          = var.instance_type
  subnet_id              = var.subnet_id

}

Aturan main

  • README.md wajib: cara run, prasyarat, daftar variable, cara destroy.
  • .gitignore Terraform yang benar (lihat chapter State).

Security Best Practices (DevSecOps)

~45 mnt▶

Bagian inti buat mindset DevSecOps. Infra aman itu hasil kebiasaan, bukan kebetulan.

Checklist keamanan IaC di AWS

  • Jangan pernah commit secret — tidak ke kode, tidak ke tfvars yang ke-push.
  • Jangan commit terraform.tfstate — bisa berisi rahasia plain.
  • Enkripsi backend S3 (encrypt = true) + aktifkan versioning.
  • Batasi akses bucket backend (IAM least-privilege, block public access).
  • IAM least privilege — kasih izin seperlunya, bukan *.
  • Kredensial sementara: IAM Role / AWS SSO / OIDC > access key statis.
  • Hindari long-lived access key — kalau terpaksa, rotasi berkala.
  • Pin versi Terraform, provider, dan module.
  • Selalu fmt + validate, dan review plan sebelum apply.
  • Pisahkan state dev/staging/prod.
  • Tagging buat ownership & cost tracking.
  • Secret di tempat yang benar: AWS Secrets Manager / SSM Parameter Store (bukan di kode).

Static analysis — scan kode sebelum apply

Pasang scanner IaC di lokal & CI buat nangkep misconfiguration (bucket publik, SG 0.0.0.0/0, dll):

terminal
checkov -d .          # Checkov (Bridgecrew/Prisma) — policy bawaan banyak
trivy config .        # Trivy config scan (penerus tfsec)
# tfsec masih dipakai, tapi sebagian fungsinya kini dilebur ke Trivy

Policy as Code

  • OPA / Conftest — tulis policy (Rego) buat cek plan/HCL di CI. Open-source, vendor-neutral.
  • Checkov custom policy — tambah aturan organisasi kamu sendiri.
  • Sentinel — policy framework HashiCorp (di HCP Terraform / Terraform Enterprise).

Secret management yang benar

secrets.tf
# Ambil secret saat runtime dari SSM Parameter Store (bukan hardcode)
data "aws_ssm_parameter" "db_password" {
  name            = "/myapp/prod/db_password"
  with_decryption = true
}
# pakai: data.aws_ssm_parameter.db_password.value
# CATATAN: nilainya TETAP masuk ke state. Lihat box di bawah.
Kenapa sensitive = true bukan berarti secret aman 100%?

sensitive = true cuma melakukan satu hal: menyembunyikan nilai dari tampilan output CLI & log. Yang TIDAK ia lakukan:

  • Nilai tetap tersimpan plain text di state file. Siapa pun yang baca state = baca secret.
  • Nilai bisa muncul di plan file (tfplan) yang kadang di-upload ke artifact CI.
  • Tidak mengenkripsi apa pun di sumbernya.

Cara aman: simpan secret di Secrets Manager/SSM, batasi akses ke state bucket seketat akses ke database, enkripsi state (encrypt = true + KMS), jangan upload plan file mentah ke artifact publik, dan minimalkan secret yang lewat Terraform sama sekali (mis. biar aplikasi ambil secret sendiri saat runtime via IAM role).

CI/CD security (sekilas, detail di chapter berikut)

  • Pakai OIDC dari CI ke AWS (kredensial sementara) — bukan menyimpan access key statis sebagai secret CI.
  • Branch protection + manual approval sebelum apply ke prod.
  • Jalankan scanner (Checkov/Trivy) sebagai gate di pipeline.
  • Jangan log plan verbose yang membocorkan nilai sensitif.

Terraform + Git + GitHub Actions

~40 mnt▶

IaC tanpa version control itu setengah jadi. Pola GitOps standar: perubahan infra lewat Pull Request, plan jalan otomatis di PR, apply baru setelah di-approve.

Alur PR yang sehat

  1. Buat branch → ubah .tf → push → buka PR.
  2. CI jalanin fmt -check, init, validate, plan → hasil plan ditempel di PR.
  3. Reviewer baca diff & plan → approve.
  4. apply jalan (idealnya butuh manual approval, apalagi untuk prod).
Auto-apply ke produksi itu bahaya

Jangan auto-apply begitu merge ke prod tanpa gerbang. Satu PR keliru bisa hapus resource. Selalu ada manual approval + branch protection untuk prod.

Autentikasi ke AWS: pakai OIDC (bukan access key statis)

OIDC > AWS_ACCESS_KEY_ID di GitHub Secrets

Daripada simpan AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY sebagai GitHub Secret (statis, rawan bocor, ribet rotasi), pakai GitHub OIDC: workflow "menukar" token identitas GitHub dengan kredensial AWS sementara via sts:AssumeRoleWithWebIdentity. Tidak ada secret jangka panjang yang disimpan.

Workflow: plan otomatis di PR

.github/workflows/terraform-plan.yml
name: terraform-plan
on:
  pull_request:
    paths: ["**.tf", "**.tfvars"]

permissions:
  id-token: write     # WAJIB untuk OIDC
  contents: read
  pull-requests: write

jobs:
  plan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS via OIDC
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-terraform
          aws-region: ap-southeast-1

      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: 1.14.6

      - run: terraform fmt -check
      - run: terraform init
      - run: terraform validate
      - run: terraform plan -no-color -input=false

Workflow apply dengan manual approval (opsional)

.github/workflows/terraform-apply.yml
name: terraform-apply
on:
  push:
    branches: ["main"]
permissions: { id-token: write, contents: read }

jobs:
  apply:
    runs-on: ubuntu-latest
    environment: production   # <- aktifkan "required reviewers" di GitHub
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-terraform
          aws-region: ap-southeast-1
      - uses: hashicorp/setup-terraform@v3
        with: { terraform_version: 1.14.6 }
      - run: terraform init
      - run: terraform apply -auto-approve -input=false

Kunci keamanannya ada di environment: production + setting "required reviewers" di GitHub → job pause sampai ada yang approve manual. -auto-approve aman di sini karena gerbang manusianya ada di GitHub.

Glosarium

~15 mnt▶

Kamus istilah versi ramah pemula. Balik ke sini kapan pun ada kata yang bikin bingung.

IaC (Infrastructure as Code)
Mengelola infrastruktur (server, jaringan, dll) lewat file kode, bukan klik manual. Bisa di-review, di-versioning, dan diulang.
Provider
Plugin penerjemah antara Terraform dan API suatu layanan (mis. AWS). Tanpa provider AWS, Terraform gak bisa "ngomong" ke AWS.
Resource
Satu objek infrastruktur yang dikelola Terraform (EC2, VPC, S3 bucket, dll). Terraform yang membuat & menghapusnya.
Data source
Mengambil info tentang sesuatu yang sudah ada (mis. AMI terbaru, VPC default) tanpa membuatnya. Read-only.
State
"Memori" Terraform: catatan resource apa yang dikelola & kondisinya. Disimpan di terraform.tfstate.
Backend
Tempat menyimpan state. Local = di laptop. Remote = di S3 (dipakai bareng tim, aman).
Locking
Penguncian state saat ada yang apply, supaya gak ada dua orang mengubah barengan & merusak state.
Module
Kumpulan resource yang dibungkus jadi komponen reusable, mirip "fungsi" di pemrograman.
Variable
Input untuk kode Terraform supaya fleksibel (mis. region, instance type) tanpa edit isi resource.
Output
Nilai yang "dikeluarkan" Terraform setelah apply (mis. IP publik EC2), buat dilihat/dipakai modul lain.
Local
Nilai turunan/temporary di dalam kode untuk menghindari pengulangan, mis. name_prefix.
Plan
Pratinjau perubahan: apa yang akan dibuat/diubah/dihapus, sebelum dieksekusi.
Apply
Eksekusi perubahan ke infrastruktur nyata sesuai plan.
Destroy
Menghancurkan semua resource yang dikelola. Sangat menentukan — pakai hati-hati.
Drift
Selisih antara kondisi nyata di AWS dan yang tercatat di state (mis. karena diubah manual lewat Console).
Idempotency
Sifat: menjalankan apply berkali-kali dengan kode sama menghasilkan kondisi akhir yang sama, tanpa efek samping berulang.
Dependency graph
Peta ketergantungan antar resource yang Terraform susun untuk menentukan urutan buat/hapus.
Immutable infrastructure
Pola: kalau perlu berubah, buat resource baru lalu ganti — bukan mengutak-atik yang lama di tempat.
Least privilege
Prinsip keamanan: beri izin seminimal yang diperlukan, tidak lebih.
Remote state
State yang disimpan di backend remote (mis. S3), bisa diakses tim & CI secara aman.
Workspace
Mekanisme bawaan Terraform untuk punya beberapa state dari satu kode (mis. default/dev). Berguna, tapi jangan untuk pemisahan env serius.

FAQ

~10 mnt▶

Pertanyaan yang paling sering muncul dari learner pemula.

Terraform vs CloudFormation, pilih mana?
CloudFormation khusus AWS; Terraform multi-cloud & ekosistemnya lebih luas. Untuk karir Cloud/DevOps yang fleksibel, Terraform pilihan aman. Skill-nya juga transferable ke provider lain.
Apakah perlu jago AWS dulu sebelum Terraform?
Perlu paham konsep dasar (VPC, EC2, IAM, S3, SG) — dan kamu sudah. Terraform cuma cara mendeklarasikannya. Justru belajar Terraform memperkuat pemahaman AWS-mu.
Aman gak ngelab pakai akun AWS pribadi?
Aman asal: pakai akun/IAM khusus belajar, aktifkan AWS Budgets ambang kecil, pakai resource murah (t3.micro), dan selalu destroy. Hindari akun yang berisi data/kerjaan nyata.
Kenapa terraform destroy minta konfirmasi terus?
Karena destroy menghapus resource nyata — itu rem keamanan. Di otomatisasi (CI) baru pakai -auto-approve, dan itu pun dengan gerbang manual approval.
State-ku rusak / nyangkut, gimana?
Jangan panik & jangan edit manual. Untuk lock nyangkut: force-unlock setelah yakin. Untuk state korup: backend S3 dengan versioning memungkinkan rollback ke versi state sebelumnya. Itu sebab versioning bucket backend wajib.
Versi Terraform yang dipakai materi ini apa?
Seri stable 1.14.x (label "Latest" di rilis resmi HashiCorp). Seri 1.15.x masih alpha saat materi ditulis, jadi belum direkomendasikan. Provider AWS seri 6.x (~> 6.0).
Masih perlu DynamoDB untuk state locking?
Tidak. Sejak Terraform 1.11 ada native S3 locking via use_lockfile = true. Argumen dynamodb_table kini deprecated. Materi ini mengajarkan cara modern; DynamoDB hanya dijelaskan sebagai legacy.
Bedanya variables.tf dan terraform.tfvars?
variables.tf = deklarasi variabel (nama, tipe, default). terraform.tfvars = nilai aktualnya. tfvars asli jangan di-commit (bisa berisi nilai sensitif); commit terraform.tfvars.example sebagai contoh.
Habis ini belajar apa?
Sesuai jalur mentoring: lanjut ke Kubernetes. Dari sisi Terraform, kamu bisa eksplor: remote state data source, Terragrunt, testing (Terratest), dan provider lain. Tapi kuasai fondasi ini dulu sampai lancar.
