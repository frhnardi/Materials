01

Kenapa Linux Penting

Sebelum hafal command, paham dulu kenapa Linux itu "tanah" tempat semua tool DevOps lo berdiri.

Penjelasan Singkat

Hampir semua server di dunia jalan di Linux — dan di AWS, mayoritas EC2 pakai Ubuntu atau Amazon Linux. Pas lo deploy Docker container, jalanin pipeline CI/CD, atau setup Kubernetes node, semuanya nempel di atas Linux. Jadi kalau lo nggak bisa baca log atau cek service di Linux, lo bakal stuck pas production error jam 2 pagi.

Hubungan dengan Tool Lo

AWS EC2Virtual server-nya = Ubuntu. Lo masuk via SSH.▶
EC2 instance itu cuma "komputer Linux di cloud". Begitu launch, cara satu-satunya ngatur dia ya lewat terminal Linux. Tanpa skill ini, EC2 cuma kotak hitam.
DockerContainer = proses Linux yang diisolasi.▶
Docker pakai fitur kernel Linux (namespaces & cgroups). Pas docker exec -it masuk ke container, yang lo ketik ya command Linux yang sama persis.
KubernetesTiap node = mesin Linux.▶
Worker node K8s adalah server Linux. Debug pod yang crash sering berakhir di journalctl dan cek resource pakai command yang lo pelajari di sini.
CI/CD · GitHub ActionsRunner default = ubuntu-latest.▶
Tiap step run: di workflow lo dieksekusi di shell Linux. Paham bash + Linux = paham kenapa pipeline lo gagal.
🎯MindsetJangan hafal semua command. Otak lo bukan Google. Yang penting: paham pattern troubleshooting — "ada masalah → cek apa dulu → command apa yang relevan". Sisanya tinggal man atau search.
⚡Mini PracticeTulis 3 tool yang lo udah pelajari (AWS, Docker, dst) dan jawab: "kalau ini error, log-nya ada di Linux mana?" — nanti dijawab di modul 8.
02

Basic Terminal & Navigation

Begitu SSH masuk ke server, hal pertama: tahu lo di mana dan siapa lo. Ini fondasinya.

Command Penting

pwdPrint Working Directory — lagi di folder mana?▶
Output-nya path absolut, misal /home/ubuntu. Selalu cek ini sebelum jalanin command yang berhubungan dengan file.
lsList isi folder. Coba ls -la.▶
ls -l = detail (permission, size, tanggal). -a = tampilkan file hidden (yang diawali titik, seperti .ssh). -h = ukuran human-readable.
cdChange Directory — pindah folder.▶
cd /var/log pindah ke path. cd .. naik satu level. cd ~ atau cd balik ke home. cd - balik ke folder sebelumnya.
clearBersihin layar (atau Ctrl+L).▶
Cuma bersihin tampilan, history tetap aman.
historyLihat command yang pernah diketik.▶
Berguna banget buat inget command panjang. Tekan ↑ buat scroll command sebelumnya, atau Ctrl+R buat search.
manManual — dokumentasi tiap command.▶
man ls buka manual lengkap. Tekan q buat keluar. Ini "Google offline" lo di server.
whoamiLagi login sebagai user siapa?▶
Penting buat tahu apakah lo ubuntu, root, atau user lain — ngaruh ke permission.
hostnameNama server ini apa?▶
Krusial pas lo buka banyak SSH session ke server berbeda biar nggak salah ketik command di server yang salah.
uname -aInfo kernel & arsitektur OS.▶
Nunjukin versi kernel Linux & arsitektur (x86_64 / arm64). Berguna pas install software yang spesifik arsitektur.

Contoh Real Case

🎯Case"Baru SSH ke EC2 Ubuntu — gimana tahu gue lagi di folder mana & server apa?" Jawab: pwd buat tahu folder, hostname buat tahu nama server, whoami buat tahu user. Tiga command ini = orientasi awal lo.
orientasi-awal.sh
$ whoami
# ubuntu
$ hostname
# ip-172-31-8-42
$ pwd
# /home/ubuntu
$ uname -a
# Linux ip-172-31-8-42 5.15.0-aws x86_64 GNU/Linux
⚠️Common MistakeKetik command destruktif tanpa ngecek posisi folder dulu. Selalu pwd + ls sebelum hapus/pindah file.
⚡Mini PracticeCoba di terminal simulator di bawah ini → ketik whoami, pwd, lalu uname -a. (Ketik help buat lihat command yang tersedia.)
ubuntu@ip-172-31-8-42: ~type "help"
Welcome to Ubuntu 22.04 LTS (simulator). Ketik help buat mulai.

03

File & Directory Management

Bikin, copy, pindah, hapus, dan baca file. Roti-mentega kerjaan harian di server.

Command Penting

mkdirBikin folder baru.▶
mkdir app bikin satu folder. mkdir -p app/logs/2026 bikin folder bertingkat sekaligus.
touchBikin file kosong / update timestamp.▶
touch index.html bikin file kosong kalau belum ada.
cpCopy file/folder.▶
cp file.txt backup.txt. Untuk folder pakai -r (recursive): cp -r app/ app-backup/.
mvPindah ATAU rename file.▶
mv old.txt new.txt = rename. mv file.txt /tmp/ = pindah. Satu command, dua fungsi.
rmHapus file. HATI-HATI.▶
rm file.txt hapus file. rm -r folder/ hapus folder + isinya. Di Linux nggak ada Recycle Bin — sekali hapus, hilang.
catTampilkan SELURUH isi file.▶
Cocok buat file kecil (config, .env). Jangan buat file log raksasa — bakal nge-flood layar.
lessBaca file besar per halaman.▶
Scroll dengan panah/PageUp-Down, search dengan /keyword, keluar dengan q. Pilihan aman buat file gede.
head / tailLihat baris awal / akhir file.▶
head -n 20 file = 20 baris pertama. tail -n 50 file = 50 baris terakhir. tail -f = follow live (penting buat log!).
nanoText editor paling gampang.▶
nano config.txt. Edit, lalu Ctrl+O simpan, Ctrl+X keluar. Rekomendasi buat pemula.
vimEditor powerful (singkat aja dulu).▶
Cukup tahu cara keluar darurat: tekan Esc lalu ketik :q! + Enter (keluar tanpa simpan). Untuk simpan: :wq. Pelajari lebih dalam nanti — nano dulu cukup.

Best Practice

💀BahayaJANGAN PERNAH ketik rm -rf / atau rm -rf * sembarangan. rm -rf / bisa menghapus seluruh sistem. Selalu baca dua kali path sebelum tekan Enter.
⚠️Common MistakeHapus file tanpa ls dulu. Biasakan: cek dengan ls → baru rm. Untuk file besar, pakai less/tail, bukan cat, biar terminal nggak nge-freeze.
file-workflow.sh
$ mkdir -p project/src
$ cd project
$ touch app.py
$ ls -la          # cek dulu sebelum aksi apapun
$ cp app.py app.py.bak
$ tail -n 20 app.py  # lihat 20 baris terakhir
⚡Mini PracticeBuat folder demo, masuk ke dalamnya, bikin file test.txt, lalu rename jadi final.txt pakai mv.

Permission & Ownership

Salah satu sumber error #1 di server: "Permission denied". Paham ini, separuh masalah lo kelar.

Konsep: rwx

Tiap file punya 3 jenis izin untuk 3 kelompok. r = read (baca), w = write (ubah), x = execute (jalankan). Tiga kelompoknya: Owner (pemilik), Group, dan Others (semua orang).

Owner
r4
w2
x1
Group
r4
-0
x1
Others
r4
-0
x1
Owner (4+2+1=7) · Group (4+0+1=5) · Others (4+0+1=5)  →  chmod 755
r = 4 readw = 2 writex = 1 execute

Command Penting

chmodUbah permission file.▶
chmod 755 file (angka) atau chmod +x file (tambah execute). 755 = owner full, lainnya read+execute (umum buat folder & script). 644 = owner read+write, lainnya read aja (umum buat file biasa seperti index.html).
chownUbah pemilik file.▶
sudo chown www-data:www-data index.html bikin Nginx (user www-data) jadi pemilik file. Format: chown user:group file.
sudoJalankan command sebagai root.▶
"SuperUser DO". Dipakai buat aksi yang butuh hak admin (install, edit file sistem). Pakai seperlunya — jangan asal sudo semua.

root vs Normal User

root = user super-admin, bisa apa aja, nggak ada rem. Normal user (misal ubuntu) = dibatasi, lebih aman. Best practice: kerja sebagai normal user, pakai sudo cuma pas perlu. Jangan login langsung sebagai root.

Contoh Real Case

🎯Case"Kenapa ./deploy.sh nggak bisa jalan? Muncul Permission denied." → File-nya belum punya izin execute. Solusi: chmod +x deploy.sh lalu jalankan lagi.
fix-permission.sh
$ ./deploy.sh
# bash: ./deploy.sh: Permission denied
$ ls -l deploy.sh
# -rw-r--r--  (belum ada 'x')
$ chmod +x deploy.sh
$ ls -l deploy.sh
# -rwxr-xr-x  (sekarang ada 'x') ✓
$ ./deploy.sh   # jalan!
⚠️Common MistakeAsal chmod 777 biar "semua bisa". Itu bahaya keamanan — semua orang bisa nulis file lo. Pakai 755 atau 644, bukan 777.
⚡Mini PracticeBikin file run.sh, cek permission-nya dengan ls -l, kasih izin execute, lalu cek lagi. Perhatikan perubahan -rw- jadi -rwx.
05

Package Management (apt)

Install software di Ubuntu = pakai apt. Ibarat "App Store" buat server, tapi lewat terminal.

Command Penting

sudo apt updateRefresh daftar paket terbaru.▶
Ini bukan meng-upgrade software, cuma update "katalog". Selalu jalankan ini dulu sebelum install apapun di server yang baru.
sudo apt upgradeUpgrade software yang udah terinstall.▶
Update semua paket ke versi terbaru. Di production, lakukan dengan hati-hati (bisa restart service).
sudo apt install <pkg>Install paket baru.▶
sudo apt install nginx -y. Flag -y = auto-yes biar nggak ditanya konfirmasi.
sudo apt remove <pkg>Hapus paket.▶
apt remove hapus software-nya. apt purge hapus sampai file config-nya juga.
apt search <kata>Cari nama paket.▶
Lupa nama persis paketnya? apt search docker bakal nampilin kandidatnya.

Contoh: Install Tool Wajib DevOps

setup-tools.sh
$ sudo apt update
$ sudo apt install curl git nginx unzip -y
# curl  → tes HTTP / download
# git   → clone repo
# nginx → web server
# unzip → ekstrak file .zip
⚠️Common MistakeLangsung apt install tanpa apt update dulu di server baru → bisa kena error "package not found" atau dapat versi lama. Urutannya selalu: update → install.
⚡Mini PracticeJalankan sudo apt update, lalu install htop (tool monitoring yang kita pakai di modul berikutnya): sudo apt install htop -y.
06

Process & Resource Monitoring

"Server kok lemot?" — modul ini ngajarin cara cek CPU, RAM, dan disk biar lo nggak nebak-nebak.

Command Penting

ps auxLihat semua proses yang jalan.▶
Snapshot proses + pemakaian CPU/RAM. Sering dikombinasi: ps aux | grep nginx buat cari proses tertentu.
topMonitor proses real-time (bawaan).▶
Tampilan live, update tiap detik. Lihat proses yang paling rakus CPU/RAM di atas. Keluar dengan q.
htopVersi top yang lebih enak dilihat.▶
Warna-warni, bisa scroll & kill proses pakai mouse/keyboard. Install dulu: sudo apt install htop.
free -hCek pemakaian RAM.▶
-h = human readable (MB/GB). Lihat kolom available buat tahu RAM yang masih bisa dipakai.
df -hCek sisa kapasitas disk.▶
Lihat kolom Use%. Disk penuh (100%) = penyebab error yang sering kelewat! Fokus ke baris /.
du -shUkuran folder tertentu.▶
du -sh /var/log = total ukuran folder log. Berguna buat nyari "siapa yang makan disk".
uptimeServer hidup berapa lama + load.▶
Angka load average nunjukin beban. Kalau jauh lebih tinggi dari jumlah CPU = server overload.

Contoh Real Case

🎯Case"Server terasa lambat, cek apa dulu?" Urutan cepat: 1) df -h — disk penuh? 2) free -h — RAM habis? 3) htop / top — proses apa yang rakus CPU? Tiga ini ngungkap 90% penyebab lemot.
why-so-slow.sh
$ df -h           # disk penuh? lihat Use%
$ free -h         # RAM habis? lihat available
$ top              # proses rakus? lihat %CPU teratas
$ du -sh /var/log # folder gemuk? sering log yang numpuk
⚠️Common MistakeLangsung restart server pas lemot tanpa diagnosa. Cek dulu — sering penyebabnya disk penuh karena log nggak pernah dibersihin, bukan butuh restart.
⚡Mini PracticeDi simulator atas, ketik df -h dan free -h. Baca: disk pakai berapa persen? RAM tersisa berapa?
07

Service Management (systemd)

Nginx, Docker, SSH — semua jalan sebagai "service". systemctl adalah remote control-nya.

Command Penting

systemctl status <svc>Cek service hidup atau mati.▶
Command yang paling sering dipakai. Cari tulisan active (running) berwarna hijau. Kalau merah failed = ada masalah.
sudo systemctl start <svc>Nyalakan service.▶
Menjalankan service yang lagi mati. Efeknya langsung, tapi nggak bikin auto-start saat reboot.
sudo systemctl stop <svc>Matikan service.▶
Hentikan service. Misal sudo systemctl stop nginx buat maintenance.
sudo systemctl restart <svc>Stop lalu start lagi.▶
Wajib dipakai setiap habis ngubah config. Tanpa restart, perubahan config nggak kebaca.
sudo systemctl enable <svc>Auto-start saat server reboot.▶
Penting! Tanpa enable, kalau EC2 di-reboot, Nginx lo nggak nyala otomatis dan website down.
sudo systemctl disable <svc>Matikan auto-start.▶
Kebalikan enable. Service nggak akan nyala otomatis saat boot.
🎯Case · NginxSetelah install Nginx, lo mau pastikan dia hidup sekarang DAN nyala otomatis kalau server reboot. Kombinasinya: sudo systemctl start nginx + sudo systemctl enable nginx.
manage-nginx.sh
$ sudo systemctl status nginx
# ● nginx.service - active (running) ✓
$ sudo systemctl enable nginx   # auto-start saat reboot
$ sudo systemctl restart nginx  # setelah edit config
⚠️Common MistakeEdit config Nginx tapi lupa restart → bingung kenapa perubahan nggak muncul. Selalu restart setelah ubah config. Dan jangan lupa enable biar tahan reboot.
⚡Mini PracticeDi simulator, ketik systemctl status nginx. Perhatikan status active (running) berwarna hijau.
08

Log & Troubleshooting

90% debugging di server = baca log. Tahu log-nya di mana & cara baca live = skill paling berharga.

Command Penting

journalctlLog terpusat dari systemd.▶
Semua log service modern ada di sini. journalctl -e langsung ke paling bawah (terbaru).
journalctl -u nginxLog service spesifik.▶
-u = unit (service). Tambah -f buat follow live: journalctl -u nginx -f. Ini cara cek kenapa Nginx gagal start.
tail -f .../access.logLihat traffic masuk secara live.▶
sudo tail -f /var/log/nginx/access.log. Tiap ada yang buka website lo, baris baru muncul. Keluar: Ctrl+C.
tail -f .../error.logLihat error Nginx secara live.▶
sudo tail -f /var/log/nginx/error.log. Tempat pertama yang dicek kalau website error 502/500.
dmesgLog level kernel (hardware/sistem).▶
Singkatnya: buat masalah dalam (out-of-memory killer, disk error). dmesg | tail buat lihat yang terbaru.

Lokasi Log Penting

log-locations
# Nginx access (siapa yang akses)
/var/log/nginx/access.log
# Nginx error (kenapa gagal)
/var/log/nginx/error.log
# Log sistem umum
/var/log/syslog
🎯Case"Website nggak bisa diakses — cek log dari mana?" → Mulai dari sudo systemctl status nginx. Kalau service ok tapi tetap error, baca sudo tail -f /var/log/nginx/error.log sambil refresh browser. Error-nya bakal muncul live di situ.
⚠️Common MistakeNebak-nebak penyebab error tanpa buka log. Log itu "kotak hitam" pesawat — di situ jawabannya. Biasakan tail -f error.log dulu sebelum panik.
⚡Mini PracticeJawab pertanyaan dari modul 1: tiap tool (Docker, Nginx) log-nya di mana? Untuk Nginx → /var/log/nginx/. Untuk service systemd → journalctl -u <nama>.

Networking Basic untuk DevOps

"Service jalan tapi nggak bisa dibuka dari browser" — biasanya masalah network/port/firewall. Ini toolkit-nya.

Command Penting

ip aLihat IP address server.▶
Nampilin IP privat server. (IP publik EC2 beda — lihat di AWS Console.) Ganti command lama ifconfig.
ping <host>Tes konektivitas ke server lain.▶
ping google.com. Kalau ada balasan = jaringan keluar OK. Stop dengan Ctrl+C.
curl <url>Tes HTTP dari terminal.▶
curl localhost ngecek apakah web server hidup dari dalam server itu sendiri. Senjata utama debugging web.
wget <url>Download file dari internet.▶
wget https://.../file.zip. Mirip curl tapi fokus ke download/simpan file.
ss -tulpnPort mana yang lagi "listen"?▶
sudo ss -tulpn. Cek apakah ada proses yang dengerin port 80/443. Pengganti modern dari netstat (yang sekarang dianggap legacy).
ufw statusCek firewall lokal Ubuntu.▶
sudo ufw status. Lihat port mana yang dibuka/ditutup oleh firewall di dalam server.
ufw allow 80 / 22Buka port di firewall.▶
sudo ufw allow 80 (HTTP), sudo ufw allow 22 (SSH). Hati-hati: jangan blok port 22 atau lo kekunci dari server sendiri!
🎯Case"Service running tapi nggak bisa diakses dari browser — cek apa aja?" Lapisan demi lapisan: 1) curl localhost jalan? (kalau ya, web server OK). 2) sudo ss -tulpn — port 80 listen? 3) sudo ufw status — firewall blok? 4) Di AWS: Security Group izinkan port 80? (ini sering banget kelupaan!).
debug-network.sh
$ curl localhost          # web server jawab? (dalam server)
$ sudo ss -tulpn         # port 80 listening?
$ sudo ufw status         # firewall ubuntu blok port?
$ sudo ufw allow 80       # buka HTTP kalau perlu
⚠️Common MistakeLupa AWS Security Group. Walau di dalam server semua hijau, kalau Security Group EC2 nggak izinin port 80, browser tetap nggak bisa konek. Ufw (dalam server) dan Security Group (di AWS) itu dua firewall berbeda.
⚡Mini PracticeDi simulator, ketik curl localhost lalu ss -tulpn. Lihat port mana yang muncul sebagai LISTEN.

SSH Basic

Pintu masuk lo ke server. Tanpa SSH, EC2 cuma ikon di dashboard AWS. Ini cara bukanya.

Konsep Inti

SSH (Secure Shell) = cara aman buat "masuk" dan ngendaliin server dari laptop lo. Di AWS, lo masuk pakai private key (file .pem) — bukan password. Konsepnya pasangan kunci: private key (rahasia, simpan di laptop) & public key (ditaruh di server). Cuma yang pegang private key cocok yang boleh masuk.

Command Penting

ssh-login.sh
# Login pakai password (kalau diaktifkan)
$ ssh ubuntu@13.250.44.10

# Login ke EC2 pakai private key (.pem)
$ chmod 400 mykey.pem        # amankan key dulu (wajib!)
$ ssh -i mykey.pem ubuntu@13.250.44.10

Folder ~/.ssh

~/.ssh/Folder rahasia tempat config SSH.▶
Folder hidden di home. Isinya kunci dan catatan koneksi. Lihat dengan ls -la ~/.ssh.
known_hostsDaftar server yang pernah lo masuki.▶
SSH nyimpen "sidik jari" tiap server di sini. Kalau berubah, SSH bakal warning (proteksi dari serangan man-in-the-middle).
authorized_keysPublic key yang boleh masuk ke server.▶
Di sisi server: ~/.ssh/authorized_keys. Siapa pun yang public key-nya ada di sini, boleh login. Inilah yang AWS isi otomatis dari key pair lo.

Password vs Private Key

Private key jauh lebih aman daripada password: nggak bisa ditebak/brute-force, dan itu standar di AWS. Password lebih praktis tapi rawan. Best practice DevOps: pakai key, matikan login password.

🎯Case"Login ke EC2 Ubuntu via SSH." → Download .pem dari AWS, set permission ketat dengan chmod 400 mykey.pem, lalu ssh -i mykey.pem ubuntu@<public-ip>. User default Ubuntu di AWS = ubuntu.
⚠️Common MistakeError "UNPROTECTED PRIVATE KEY FILE" = permission .pem terlalu terbuka. Fix: chmod 400 mykey.pem. Mistake lain: salah user (pakai root@ padahal harusnya ubuntu@).
⚡Mini PracticeLihat isi folder SSH lo sendiri: ls -la ~/.ssh. Kenali file known_hosts dan kunci yang ada.

Web Server Mini Module (Nginx)

Gabungin semua yang lo pelajari: install web server, jalanin, dan sajikan halaman ke dunia.

Apa itu Web Server?

Web server = program yang "mendengarkan" request dari browser di port 80 (HTTP) / 443 (HTTPS) dan ngirim balik halaman web. Nginx & Apache adalah yang paling populer.

Nginx vs Apache (singkat)

Nginx ringan, cepat, jago handle banyak koneksi sekaligus — favorit DevOps modern, sering jadi reverse proxy. Apache lebih tua, fleksibel dengan .htaccess. Untuk track DevOps/Cloud, fokus Nginx dulu.

Folder Penting

Secara default, Nginx menyajikan file dari /var/www/html. File index.html di situ = halaman depan website lo.

Alur Lengkap

deploy-nginx.sh
# 1. Update & install
$ sudo apt update
$ sudo apt install nginx -y

# 2. Pastikan jalan & aktif saat reboot
$ sudo systemctl status nginx
$ sudo systemctl enable nginx

# 3. Tes dari dalam server
$ curl localhost

# 4. Edit halaman depan
$ cd /var/www/html
$ echo "<h1>Hello from Ubuntu Server</h1>" | sudo tee index.html

# 5. Restart setelah perubahan
$ sudo systemctl restart nginx

# 6. Pantau log secara live
$ sudo tail -f /var/log/nginx/access.log
$ sudo tail -f /var/log/nginx/error.log
🎯CaseSetelah langkah di atas, buka browser ke http://<public-ip-ec2>. Muncul "Hello from Ubuntu Server"? Berarti dari install sampai serving — semua jalan. Setiap kali lo refresh, lihat baris baru muncul di access.log.
⚠️Common Mistakeecho ... > index.html (tanpa sudo) gagal karena /var/www/html butuh hak root. Solusi: pakai sudo tee seperti contoh, atau edit dengan sudo nano index.html.
⚡Mini PracticeDi simulator, ketik curl localhost lalu cat index.html. Lihat HTML yang disajikan Nginx.

Troubleshooting Flow

"Website down!" — jangan panik. Ikuti urutan ini dari atas ke bawah. Hampir selalu ketemu di salah satu langkah.

1
Server-nya hidup?
Coba SSH atau cek di AWS Console apakah instance "running".
ssh ubuntu@<ip>
2
SSH bisa masuk?
Kalau nggak bisa → masalah jaringan/Security Group/key.
ssh -i key.pem ubuntu@<ip>
3
Service Nginx jalan?
sudo systemctl status nginx
Kalau failed → sudo systemctl restart nginx
4
Port 80 listening?
sudo ss -tulpn | grep :80
5
Firewall blok?
sudo ufw status
Cek juga AWS Security Group — dua firewall berbeda!
6
Apa kata log Nginx?
sudo tail -f /var/log/nginx/error.log
7
Disk penuh?
df -h
Use% di 100%? Penyebab tersembunyi yang sering kelupaan.
8
Restart service kalau perlu
sudo systemctl restart nginx
Langkah terakhir setelah penyebab ketemu & diperbaiki.
🧭PrinsipTroubleshooting itu berlapis dari luar ke dalam: server → akses → service → port → firewall → log → resource. Jangan loncat-loncat. Disiplin ngikutin urutan = nemu masalah lebih cepat daripada nebak.
